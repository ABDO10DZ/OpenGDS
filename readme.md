# OpenGDS v1.0 - release 

**A Python-based Godot GDScript bytecode inspector, decompiler, compiler, disassembler, and security auditor.**  
By **ABDO10_DZ / 0xbytecode**

OpenGDS works with Godot's compiled GDScript binary-token container format (`.gdc`, GDSC). It can inspect compiled files, reconstruct readable GDScript, and compile `.gd` source files into GDSC v101 containers. It also provides token disassembly, decoded-payload hexadecimal dumps, constant extraction, recursive batch processing, and heuristic static security checks.

The current implementation targets **GDSC bytecode version 101**. Its compiler implements GDScript tokenization and GDSC token-buffer serialization in Python, based on Godot's open-source implementation. The supported workflow does not require launching the Godot editor.

> **Beta status:** The latest `dcmp` → `comp` workflow produced byte-identical `.gdc` files for all 1,130 files in the supplied GDSC v101 corpus. This result applies to that tested corpus and to sources freshly generated by the updated `dcmp`. It does not establish exhaustive support for every possible GDScript construct or every Godot release.

## 🚀 Features

| Feature | Command | Description |
|---|---|---|
| **GDScript Reconstruction** | `dcmp` | Reconstructs readable GDScript from compiled GDSC token data, using stored token line and column metadata. |
| **GDScript Token-Buffer Compilation** | `comp` | Converts `.gd` files into Godot-compatible GDSC v101 `.gdc` containers using the Python tokenizer and serializer. |
| **File Information** | `info` | Reports the GDSC signature, bytecode version, file and payload sizes, compression, SHA-256, and structural counts when supported. |
| **Disassembly** | `disasm` | Displays decoded tokens, including token types, arguments, source lines, columns, and token text. |
| **Hexadecimal Dump** | `hexdump` | Displays the hexadecimal representation of the decoded GDSC payload. |
| **Constant Extraction** | `consts` | Extracts and displays constants stored in the compiled script. |
| **Static Security Audit** | `audit` | Checks decoded constants and token text for selected secret patterns, URLs, and security-sensitive API references. |
| **Recursive Batch Processing** | All modes | Processes matching files recursively and preserves relative directory structure in generated output. |
| **GDSC v101 Validation** | `info` and decoding modes | Validates the supported GDSC version and rejects unsupported versions during decoding. |
| **Zstandard Support** | `info`, decoding, `comp` | Reads compressed GDSC files and generates compressed output; `comp` can also write an uncompressed container. |

## 🔄 Bidirectional GDSC Workflow

OpenGDS supports both directions between GDSC v101 files and GDScript source:

```text
       GDSC v101 (.gdc)
               |
         +-----+-----+
         |           |
       dcmp         info
         |
         v
    GDScript (.gd)
         |
        comp
         |
         v
    GDSC v101 (.gdc)
```

The `comp` implementation generates a GDScript binary-token buffer. Its work includes:

- GDScript tokenization.
- Identifier table generation.
- Constant pool generation and deduplication.
- Variant serialization.
- Token type and argument encoding.
- Token line and column metadata.
- GDSC v101 header generation.
- Optional Zstandard compression.

**Scope:** `comp` implements tokenization and GDSC token-buffer serialization. It is not a replacement for Godot's complete GDScript parser, semantic analysis, type checker, project importer, or project build pipeline.

## 📋 Command-Line Interface

```text
python3 OpenGDS.py <mode> <file-or-folder> [options]
```

### Modes

| Command | Input | Description |
|---|---|---|
| `info` | `.gdc` | Inspect GDSC file metadata and validate supported v101 structure. |
| `comp` | `.gd` | Compile GDScript into a GDSC v101 `.gdc` file. |
| `dcmp` | `.gdc` | Decompile/reconstruct GDScript. |
| `hexdump` | `.gdc` | Dump decoded payload bytes in hexadecimal. |
| `consts` | `.gdc` | Extract constants. |
| `audit` | `.gdc` | Run heuristic static security checks. |
| `disasm` | `.gdc` | Display the decoded token stream. |

Analysis and decompilation modes accept `.gdc` input. The `comp` mode accepts `.gd` input. Each mode also accepts a directory and recursively searches for its expected file extension.

### Examples

**Inspect a compiled file**

```bash
python3 OpenGDS.py info assets/game.gdc
```

**Compile one GDScript file**

```bash
python3 OpenGDS.py comp game.gd
```

**Compile a directory recursively**

```bash
python3 OpenGDS.py comp ./scripts/
```

**Decompile one compiled file**

```bash
python3 OpenGDS.py dcmp assets/game.gdc
```

**Decompile a directory recursively**

```bash
python3 OpenGDS.py dcmp assets/
```

**Extract constants**

```bash
python3 OpenGDS.py consts assets/game.gdc
```

**Disassemble tokens**

```bash
python3 OpenGDS.py disasm assets/game.gdc
```

**Dump the decoded payload**

```bash
python3 OpenGDS.py hexdump assets/game.gdc
```

**Run the security audit**

```bash
python3 OpenGDS.py audit assets/
```

## ⚙️ Options

The current CLI exposes these options:

| Option | Description |
|---|---|
| `-o`, `--output PATH` | Output file for single-file input, or output root for directory input. |
| `--outdir PATH` | Set the output root for directory processing. |
| `--continue-on-error` | Continue recursive processing after an individual file fails. |
| `--tab-size N` | Tab width used when measuring source columns during compilation. Default: `4`. |
| `--no-compress` | Write uncompressed GDSC token data. Applies to `comp`. |
| `--force` | Allow `comp` to overwrite existing output files. |

Examples:

```bash
# Compile without Zstandard compression
python3 OpenGDS.py comp game.gd --no-compress

# Allow an existing output to be replaced
python3 OpenGDS.py comp game.gd --force

# Set the source tab width
python3 OpenGDS.py comp ./scripts/ --tab-size 4

# Continue processing after an individual compilation error
python3 OpenGDS.py comp ./scripts/ --continue-on-error

# Choose an output directory
python3 OpenGDS.py comp ./scripts/ --outdir ./build/
```

By default, `comp` does not overwrite an existing `.gdc` output. Use `--force` to permit replacement.

## 📂 Recursive Batch Processing

When a directory is supplied, OpenGDS searches its subdirectories for the extension expected by the selected mode and preserves relative paths in the output tree.

### Compilation example

Input:

```text
scripts/
├── player.gd
├── game.gd
└── entities/
    ├── enemy.gd
    └── boss.gd
```

Default output:

```text
scripts.comp/
├── player.gdc
├── game.gdc
└── entities/
    ├── enemy.gdc
    └── boss.gdc
```

### Decompilation example

Input:

```text
assets/
├── player.gdc
└── entities/
    └── enemy.gdc
```

Default output:

```text
assets.dcmp/
├── player.gd
└── entities/
    └── enemy.gd
```

For other analysis modes, generated files use the corresponding mode-specific output directory and extension.

## ℹ️ File Information (`info`)

The `info` command reports metadata from the GDSC header and validates supported v101 payloads.

Reported fields include:

- GDSC signature.
- Bytecode version.
- File size and header size.
- Stored payload size.
- Compression status.
- Declared decoded size, when present.
- SHA-256 of the complete file.
- Identifier, constant, line-map, column-map, and token counts for a valid v101 payload.

The GDSC header does **not** encode the exact Godot engine release. Accordingly, `info` reports the engine release as not encoded rather than inferring it from the bytecode version.

For a version other than v101, `info` can display available header metadata but does not attempt to decode an unsupported payload.

## 🔐 Static Security Audit (`audit`)

`audit` is intended for defensive reverse engineering and security research. It scans decoded constants and token text for selected indicators, including:

- Private-key markers.
- JWT-like strings.
- API-key, secret-key, access-token, client-secret, password, and similar assignments.
- AWS access-key patterns.
- GitHub token patterns.
- Generic secret/token/credential assignments.
- Embedded HTTP and HTTPS URLs.
- References to selected dynamic or external execution APIs, including `OS.execute`, `OS.shell_open`, `JavaScriptBridge`, `load_string`, and `ResourceLoader.load`.

Secret-like values are redacted in findings. URL and API-reference findings are heuristic indicators for manual review.

**Audit limitations:** the checks are pattern-based. Findings may be false positives, and the absence of findings is not proof that a script is secure. The audit does not perform full control-flow analysis, data-flow analysis, or vulnerability proof.

## 🧪 Validation Status

OpenGDS uses a regression workflow that compares generated binaries against original files rather than treating successful compilation alone as proof of compatibility.

### Supplied GDSC v101 corpus — full round-trip test

The supplied original archive contained **1,130 `.gdc` files**. The latest release was tested by inspecting and decompiling every original file, compiling the freshly decompiled sources, and comparing each rebuilt file with its original counterpart.

| Test | Result |
|---|---:|
| Original `.gdc` files | 1,130 |
| `info` validations | 1,130 / 1,130 |
| `dcmp` operations | 1,130 / 1,130 |
| `comp` operations on fresh `dcmp` output | 1,130 / 1,130 |
| Exact SHA-256 matches | **1,130 / 1,130** |
| Compilation failures | 0 |
| Hash mismatches | 0 |
| Rebuilt file-size differences | 0 |

The full-corpus run completed without CLI stderr output. No Godot editor executable was launched or required. The compiler used the system `libzstd` shared library for compressed output; the existing decoding path uses the `zstd` command-line utility for compressed payloads.

### Important distinction: older decompiled source archive

The separately supplied older `.gd` archive also contained 1,130 source files and was compiled successfully:

```text
Compilation:             1,130 / 1,130
Exact original SHA-256:      28 / 1,130
```

Those older source files did not preserve all original token-position metadata required for byte-identical reserialization. This does not contradict the full round-trip result above: the **1,130 / 1,130** exact result was achieved using `.gd` files freshly generated by the latest, position-preserving `dcmp` implementation.

This distinction matters because arbitrary `.gd` source does not necessarily contain enough information to reproduce every metadata choice in an existing `.gdc` file. Compilation success and byte-identical reproduction are separate claims.

### PR #1 regression

The same-line `else: if` indentation issue reported in PR #1 was reviewed against the latest implementation and tested through the CLI. The latest reconstruction algorithm retains the same-line `else: if` structure and nested body indentation.

```text
5 regression checks passed
0 regression checks failed
```

The issue was already handled by the current position-driven reconstruction path, so no additional source change was required for this report.

### Earlier Godot 4.6.2 sample coverage

A previously supplied 693-file GDSC v101 corpus was also used for a representative 20-file test across the five original analysis modes:

```text
20 files × 5 modes = 100 operations
100 successful
0 failures
```

This was a representative sample, not a full 693-file round-trip test.

### Reproducibility evidence

The full-corpus verification CSV records each file's relative path, original and rebuilt sizes, original and rebuilt SHA-256 values, and match result.

The byte-identical acceptance condition is:


## 🧬 GDSC Compatibility

Current supported target:

```text
Container:       GDSC
Bytecode version: 101
Compression:     Zstandard or uncompressed payload
```

The supplied validation material includes GDSC v101 files associated with Godot 4.x. Multiple Godot releases can use the same GDSC bytecode version; the version field alone does not identify the exact engine release.

OpenGDS explicitly checks the GDSC version and does not attempt normal decoding of unsupported versions.

### Not currently guaranteed

- Godot 3.x bytecode.
- GDSC versions other than v101.
- Encrypted `.gde` scripts.
- Compatibility with every future Godot tokenizer or serialization change.
- Exhaustive tokenization of every possible GDScript language construct.
- Full Godot semantic parsing, type checking, or project compilation.

## ⚠️ Limitations

### Comments and source-only information

Comments are not reliably represented in compiled GDSC token data. As a result, a decompiled source file may not contain the original comments or comment-only lines.

```text
original source
      ≠
decompiled source
```

This difference does not by itself indicate a tokenization or binary reconstruction problem.

### Formatting and token positions

The updated decompiler uses stored token line and column metadata when reconstructing source. This is important for the verified round-trip workflow because token-position data is part of the serialized GDSC structure.

An arbitrary `.gd` file may not preserve the exact original metadata of a compiled file. Consequently, a newly compiled `.gdc` can be valid and structurally decodable without being byte-identical to a different original `.gdc`.

### Compilation versus semantic validation

`comp` creates GDSC v101 token buffers. It does not replace the full Godot parser, type checker, or project build process. A successful `comp` run should not be interpreted as proof that the script is semantically valid in a particular Godot project.

## ⚙️ Installation

### Requirements

- Python 3.
- The Zstandard command-line utility (`zstd`) to decode compressed GDSC files.
- The system Zstandard shared library (`libzstd`) to generate compressed output with `comp`.

The exact tested environment for the 1,130-file run was Python **3.13.5**, Zstandard CLI **1.5.7**, and the system `libzstd` shared library.

### Termux / Android

```bash
pkg update
pkg install python zstd
```

### Debian / Ubuntu

```bash
sudo apt update
sudo apt install python3 zstd libzstd1
```

### macOS

With Homebrew:

```bash
brew install python zstd
```

Make sure the Zstandard executable and shared library can be found by the environment running Python.

### Windows

Install Python 3 and provide a compatible Zstandard command-line executable and shared library that can be located by the process. The availability and discovery of `libzstd` depend on the Windows environment.

No Godot editor executable is required for the implemented GDSC v101 token-buffer compilation workflow.

## 🛠️ Development / Regression Testing

The recommended development loop is:

```text
Original GDC
     |
     v
    info
     |
     v
    dcmp
     |
     v
Fresh GD sources
     |
     v
    comp
     |
     v
Rebuilt GDC
     |
     v
SHA-256 comparison
     |
     v
Identify divergence
     |
     v
Fix implementation
     |
     v
Rerun the complete corpus
```

Whenever the decoder, reconstruction, tokenizer, or serializer changes, rerun the available regression corpus. Record compile failures, missing outputs, size differences, and hash mismatches separately.

A successful compiler exit code alone is not sufficient to claim byte-identical compatibility.
